# 快递助手 ERP 工单分析

读取快递助手内部工单的基本信息和完整处理记录，提炼问题根因，并输出可直接用于产品、技术和 TB 任务流转的标准总结。整个流程只读，不回复工单、不转交、不催办、不修改状态。

## When to Use

- 用户发送 `https://ticket.kuaidizs.cn/` 工单链接，或直接提供明确工单号（如“工单编号 40311”），并要求查看、分析或总结。
- 需要将客服和技术沟通记录整理成结构化问题说明。
- 需要根据工单生成业务化的 TB 任务名称、复现步骤和期望结果。

不要用于：代替用户回复工单、改变工单状态、转交处理人或批量导出商家隐私数据。

## Prerequisites

- macOS 上的 Google Chrome 已登录快递助手内部工单系统。
- Python 可导入 `browser_cookie3`。
- 当前网络可以访问 `ticket.kuaidizs.cn`。
- 工单链接中包含 `ticketid` 参数。

首次使用若缺少 `browser_cookie3`，应在隔离环境中安装，不要修改系统 Python：

```text
terminal(command="uv venv .venv && uv pip install --python .venv/bin/python browser-cookie3", timeout=120)
```

## How to Run

技能附带只读脚本 `scripts/fetch_ticket.py`。从用户链接提取工单号后执行：

```text
terminal(command="python3 productivity/kdzs-ticket-summary/scripts/fetch_ticket.py 40039 --output /tmp/ticket-40039.json", timeout=60)
```

脚本会：

1. 从 Chrome 获取 `ticket.kuaidizs.cn` 的登录 Cookie。
2. 读取工单基本信息。
3. 读取工单全部沟通及操作记录。
4. 将结果写入指定 JSON 文件。

脚本不会打印或保存登录 Token，也不会调用任何写入接口。

## Procedure

### 1. 提取工单号

从链接的 `ticketid` 参数提取纯数字工单号；若用户直接提供唯一的纯数字工单号，直接使用该编号查询。

**完成标准：** 得到唯一的数字工单号；链接缺失且编号也未明确时，请用户补充有效链接或工单号。

### 2. 读取原始数据

运行 `scripts/fetch_ticket.py`，然后用 `read_file` 读取输出 JSON。

必须同时读取：

- 基本信息：标题、描述、商家手机号、模块、平台、状态、关联 TB。
- 完整记录：评论、排查结论、日志摘要、人员转交与处理结果。

脚本会使用工单的 `accountEncode` 调用 `POST /ticket/decodeAccount` 解密商家手机号，并返回 `merchantPhone`。手机号仅用于本次工单总结；不得写入长期记忆、日志或 Git 提交，且不得提交含完整手机号的临时原始工单 JSON。

**完成标准：** 基本信息查询返回一条工单，处理记录数量与接口返回的 `total` 一致；若工单有 `accountEncode`，则已获取 `merchantPhone`，否则明确标记为“未提供”。

### 3. 识别涉及技术

仅保留实际参与以下行为的技术人员：

- 执行技术排查或数据核对。
- 给出明确技术判断或根因。
- 提出修复、优化或临时处理方案。

排除：纯客服交班、机械转交、仅说“已同步”、产品接收及仅创建 TB 的人员。

输出时只写姓名，多人使用中文顿号 `、` 分隔，不描述分工。

### 4. 重建排查链路

按逻辑顺序压缩工单记录，并且**必须使用 `1. 2. 3.` 的有序编号输出**：

1. 用户反馈和表面现象。
2. 初始判断及验证动作。
3. 关键数据、日志或对照结果。
4. 最终根因。
5. 临时处理方案和后续流转结果。

不要逐条复述所有转交记录，也不要把初始猜测当作最终结论。

### 5. 提炼问题核心

问题核心需回答三层内容：

- **表面现象：** 用户具体看到了什么问题。
- **直接原因：** 哪个业务环节或处理结果异常。
- **机制根因：** 为什么会发生，以及影响了什么后续流程。

技术字段、SQL、接口和代码逻辑可用于解释根因，但不得无依据推断。

### 6. 生成 TB 任务名称

任务名称必须采用业务视角：

```text
业务对象或场景 + 用户可感知的问题现象 + 修复/优化
```

要求：

- 不添加 `【模块】` 前缀。
- 不出现字段名、表名、接口名、SQL 或代码实现。
- 不包含商家 ID、订单号等个案数据。
- 简洁、自然，可直接粘贴为 TB 标题。

正确示例：

```text
监控视频按快递单号查询搜索不到问题修复
```

错误示例：

```text
【监控视频】查询未兼容 bizCode 字段问题修复
```

### 7. 生成复现步骤和期望结果

复现步骤只能来自工单明确描述或可可靠还原的操作链路。信息不足时写“工单未提供明确复现步骤”，不得臆造。

期望结果从业务视角描述修复后用户应看到的正确表现，并与问题现象直接对应。信息不足时写“工单未提供明确期望结果”。

### 8. 输出固定模板

```markdown
## 工单总结

### 商家手机号
`<merchantPhone 或未提供>`

### 涉及技术
<姓名1>、<姓名2>

### 排查过程
1. <用户反馈/初始现象>
2. <排查动作与结果>
3. <最终定位>
4. <处理或流转结果>

### 问题核心
<表面现象、直接原因、机制根因及影响>

### 一句话总结
**<现象 + 根因 + 处理方向>**

### 任务名称
**<业务对象/场景 + 用户可感知的问题现象 + 修复/优化>**

### 复现步骤
1. <步骤>
2. <步骤>

### 期望结果
<修复后用户应看到的正确业务结果>
```

## Pitfalls

1. **未解密手机号：** 商家手机号必须取工单 `accountEncode` 调用 `POST /ticket/decodeAccount` 后返回的 `data.accountDecode`；不得使用脱敏 `account`，也不得将 `userId` 作为手机号。
2. **技术人员识别过宽：** 纯转交、同步和产品接收人员不计入“涉及技术”。
3. **标题过于技术化：** 字段名和代码根因放在“问题核心”，TB 任务名称只描述业务问题。
4. **猜测复现链路：** 工单没有证据时留空，不要补写看似合理的步骤。
5. **忽略历史结论变化：** 以完整记录中的最终定位为准，保留从假设到结论的关键变化。
6. **隐私和认证信息泄露：** 不输出 Cookie、Token 或 Authorization 请求头；不将完整手机号或含完整手机号的原始工单 JSON 提交到 Git；手机号只用于当前工单总结。
7. **误执行写操作：** 仅读取接口；禁止回复、转交、催办、结单或更新状态。

## Verification

输出前逐项检查：

- [ ] 基本信息与全部处理记录均已读取。
- [ ] 商家手机号来自 `POST /ticket/decodeAccount` 返回的 `data.accountDecode`；未使用脱敏 `account` 或 `userId` 替代。
- [ ] 涉及技术仅含真实参与排查和定位的技术人员。
- [ ] 排查过程体现从现象、验证到最终结论的完整链路，且以 `1. 2. 3.` 有序编号呈现。
- [ ] 问题核心解释了“为什么发生”。
- [ ] 一句话总结包含现象、根因和处理方向。
- [ ] 任务名称采用业务视角，无模块前缀和技术实现细节。
- [ ] 复现步骤有证据支撑，期望结果与问题现象直接对应。
- [ ] 输出中没有登录凭证；完整手机号仅用于当前工单总结，未提交至 Git 或长期保存。
