# 助手ERP多平台多店铺经营分析

依赖 `kdzs-erp-api-connector` 读取助手ERP数据，生成日报、周报、月报或自定义周期的经营分析。默认只读，不修改订单、库存、备注或店铺配置。

## When to Use

用户表达以下意图时加载：

- 生成经营日报、周报、月报或经营分析；
- 对比多个平台或多个店铺；
- 分析销售、利润、售后或物流表现；
- 查找增长、下滑、亏损、高退款或履约异常对象。

不要用于：创建采购单、修改订单、调整库存或查询当前不受开放平台支持的平台数据。

## Prerequisites

### 新商家接入引导

在要求商家提供 API 凭证前，先确认商家是否已经注册并开通快递助手 ERP 开放平台能力：

1. 未注册快递助手 ERP：引导商家访问 `https://erp.kuaidizs.cn` 完成注册和登录。
2. 已注册但尚未获取 API 能力：引导商家进入快递助手 ERP 的 `设置 → API开放平台`，按页面指引获取或开通 API 能力，并安全配置 `appKey`、`appSecret`。
3. 已完成上述配置：继续执行连接器加载与只读连通性验证。

不得要求商家在对话中直接发送完整 `appSecret`、Token 或 Session；应优先引导其写入安全配置。完成标准：商家已注册 ERP，且开放平台 API 凭证已安全配置。

### API 执行前提

1. 加载 `kdzs-erp-api-connector`，遵守其认证、平台、分页和错误处理规则。
2. 使用当前商家自己的 `appKey`、`appSecret` 与环境配置，不在回复中显示完整凭证、Token 或 Session。
3. 正式分析前用低风险只读接口验证连接，只有 `code=200` 且 `data.success=true` 才继续。
4. 当前开放平台不支持淘宝、天猫、1688、淘工厂和拼多多；报告必须显示未覆盖范围。

## Mandatory Report-Version Gate

**这是所有经营日报、周报、月报和自定义经营分析的强制前置步骤。**

商家触发方案后，在调用ERP接口前先问：

> 这次您需要哪种汇报版本？
>
> - 简约版：核心结论、关键数据、主要问题、下一步建议，适合快速查看。
> - 详细版：增加平台、店铺、商品、利润、售后、物流、数据口径和异常明细，适合深度复盘。

规则：

1. 商家未选择前，不调用经营分析接口，不生成报告。
2. 不因上一次选择而擅自沿用；只有商家明确要求“以后默认简约版/详细版”时才保存偏好。
3. 用户已在同一句话中明确“简约版”或“详细版”时，不重复询问。
4. 版本确认后，只补问仍然缺失且会改变查询范围的信息。
5. 用户只说“生成经营日报”时，周期默认昨天的完整自然日，但版本仍必须确认。
6. 用户只说“本周分析”时，统计本周截至昨天的完整自然日；若今天是周一，本周尚无完整自然日，应说明并询问是否改为上周。

## Procedure

### 1. 确认报告版本

执行 `Mandatory Report-Version Gate`。完成标准：已明确记录 `report_mode=simple` 或 `report_mode=detailed`。

### 2. 确认查询范围

仅补问缺失项：

- 分析周期；
- 对比周期；
- 全部支持平台或指定平台/店铺；
- 销售、利润、售后、物流或综合经营；
- 大促、直播、停店、缺货等特殊事件。

低风险默认值：

- 日报：昨天，对比前一天；
- 本周：本周截至昨天，对比上周相同星期范围；
- 近7天：截止昨天的7个完整自然日，对比此前7天；
- 月报：本月截至昨天，对比上月相同天数。

完成标准：本期和对比期天数、时间类型、平台及店铺范围一致。

### 3. 连接与覆盖检查

1. 验证 Token、Session 和只读接口。
2. 记录接口支持平台、实际返回平台和未覆盖平台。
3. 检查测试店铺、测试商品和异常名称。
4. 检查聚合报表 `total`、返回行数和分页上限。

出现接口错误时原样反馈 `code`、`message`、`traceId` 并停止，不猜测原因、不自动重试或调整参数。

### 4. 读取聚合数据

按 `references/api-workflow.md` 读取：

1. 毛利润概览；
2. 平台维度；
3. 店铺维度；
4. 售后平台、店铺和原因；
5. 物流预警。

详细版再按需读取货品/SKU维度。订单和售后明细仅在发现异常后、范围明确时下钻，不默认抓取全量。

### 5. 数据质量门禁

按 `references/safety-gates.md` 检查：

- 测试数据；
- 金额或成本异常；
- 货品映射覆盖不足；
- 汇总重复；
- 分页不完整；
- 平台未覆盖；
- 售后与销售时间口径不一致。

关键数据不可信时，报告降级为“链路验证/数据质量报告”，不能包装成正式经营结论。

### 6. 分析和分级

分析顺序：

```text
整体 → 平台 → 店铺 → 商品（详细版）→ 售后 → 物流 → 行动建议
```

行动优先级：

- P0：异常数据、重大亏损、退款或履约风险，立即处理；
- P1：销售和利润同步增长，可重点投入；
- P2：规模较大但利润、售后或履约需要优化；
- P3：样本不足或波动未超过阈值，继续观察。

每条建议必须包含对象、指标、原因和动作。

### 7. 按版本输出

使用 `references/output-templates.md`。

**简约版硬限制：**

- 一句话核心结论；
- 3—5个关键指标；
- 最多3个主要问题；
- 最多3条建议；
- 一行范围与风险提示；
- 不主动展示API名、公式、长表格、完整排行或原始明细。

**详细版要求：**

- 核心结论仍放最前；
- 展开整体、平台、店铺、商品、售后、物流和P0—P3；
- 显示口径、范围、异常和未覆盖平台；
- 不堆砌无结论的原始数据。

### 8. 安全收尾

删除临时 Token/Session 文件。只保留脱敏后的分析结果和必要聚合数据。完成标准：临时认证文件不存在，回复中不含凭证和买家隐私。

## Pitfalls

1. 售后申请时间与销售付款时间不是同一订单批次；只能称“期间退款金额占比”，不能误称真实退款率。
2. 助手ERP利润是接口口径，不等于财务会计净利润。
3. 成本、运费或退款成本缺失时，利润分析标记为“待校准”。
4. 总览接口可能返回重复汇总行，先去重再计算。
5. 店铺关联优先使用 `sellerId`，不要仅按同名店铺合并。
6. 不支持平台的数据缺失不能解释为销售为0。
7. 简约版不是少分析，而是少展示；内部仍需完成数据质量检查。
8. 详细版不是越长越好，必须结论前置且只展开有效信息。

## Verification

完成前逐项确认：

- [ ] 商家已选择简约版或详细版；
- [ ] 本期、对比期和覆盖范围明确；
- [ ] ERP响应成功且结果完整性已检查；
- [ ] 未覆盖平台已披露；
- [ ] 测试数据和异常数据已标记或排除；
- [ ] 输出严格符合所选版本；
- [ ] 每条重要结论可追溯到指标；
- [ ] 无买家隐私、完整凭证、Token 或 Session；
- [ ] 临时认证文件已删除。
